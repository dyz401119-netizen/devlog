## 背景

经常有人问：Hugo / Hexo 这类静态博客，到底需要多大的服务器？

网上的答案从「1 核 1G 绰绰有余」到「至少 2 核 4G」都有，但很少给出**具体数字**。

我手上正好有台阿里云香港的机器，2 核 1.8G 内存、40G 磁盘，上面跑着一个 Hugo 静态站（Docker + Nginx）。本文把所有能测的数字都测了一遍。

## 测试环境

| 项目 | 配置 |
|---|---|
| CPU | Intel Xeon Platinum @ 2.5GHz，2 vCPU |
| 内存 | 1870 MB（无 Swap） |
| 磁盘 | 40 GB（`/dev/vda3`） |
| 系统 | Alibaba Cloud Linux 3，内核 5.10 |
| 软件 | Docker 26.1.3 / Nginx 1.27.5 (alpine) / Hugo 0.170.0 |
| 站点 | Hugo + PaperMod 主题，5 篇文章，21 个 HTML 页面 |

## 一、运行时内存：10 MB

```bash
$ docker stats --no-stream
NAME          CPU %    MEM USAGE / LIMIT     MEM %
blog-nginx    0.00%    10.24MiB / 1.827GiB    0.55%
```

**Nginx 容器常驻 10.24 MB。**

这就是静态站最核心的优势——**Nginx 只是把文件从磁盘读出来发给客户端**，没有后端进程、没有数据库连接池，内存占用基本等于 Nginx 自身的开销。

对比一下常见的服务：

| 服务类型 | 典型内存占用 |
|---|---|
| **Nginx 静态站** | **10 MB** |
| Nginx + PHP-FPM | 200–500 MB |
| Node.js 应用 | 80–300 MB（取决于依赖） |
| Java Spring Boot | 500 MB – 1 GB+ |
| MySQL | 300 MB – 1 GB+ |
| MySQL + Redis + 应用 | 1 GB+ |

**这台机器的 1.8G 内存，跑静态站只用了 0.55%。**

宿主机整体：

```bash
$ free -m
              total        used        free      shared  buff/cache   available
Mem:           1870         417         235           2        1369        1453
```

`used` 417 MB 里，大部分是系统本身和其他进程（如 Aliyun 的监控 agent），真正的站点只占 10 MB。

## 二、磁盘占用：412 KB

站点产物：

```bash
$ du -sh site/public
412K    site/public
```

**25 个文件（21 个 HTML + CSS/JS/JSON/XML），总共 412 KB。**

明细分项：

```
128K    tags/          # 标签页
 84K    posts/         # 文章页
 52K    assets/        # CSS
 44K    categories/    # 分类页
 20K    about/         # 关于页
 16K    index.json     # 搜索索引
```

Docker 镜像占大头：

```bash
$ docker system df
TYPE            TOTAL     ACTIVE    SIZE
Images          1         1         48.22MB
```

**Nginx alpine 镜像 48 MB。** 加上镜像也就 48 MB 出头。

**对比动态博客（如 WordPress）：**

| 项目 | 静态站 | WordPress |
|---|---|---|
| 程序文件 | 0（Nginx 镜像自带） | ~50 MB |
| 数据库 | 0 | 几十 MB 起 |
| 上传的媒体文件 | 视内容而定 | 视内容而定 |
| **合计（不含内容）** | **~48 MB** | **~100 MB+** |

**这台 40G 的盘，用来放静态站能放下 8 万个同样大小的站点。**

## 三、构建耗时：0.13 秒

用 `time` 测三次 Hugo 构建：

```bash
$ cd site
$ time hugo build --destination public --gc --minify --cleanDestinationDir

  第 1 次: 0.19 秒, 峰值内存 69636 KB
  第 2 次: 0.14 秒, 峰值内存 69448 KB
  第 3 次: 0.13 秒, 峰值内存 68520 KB
```

**21 个页面，0.13 秒构建完成，峰值内存 68 MB。**

注意：这是**构建时**的峰值内存，构建结束后进程就退出了，不像动态站点那样常驻。

**为什么这么快？**

- Hugo 是 Go 写的，编译成单个二进制，没有运行时解释器开销
- 只处理 Markdown → HTML，不做数据库查询
- 增量构建友好（改一篇文章不会重建全部）

**对比 Node.js 系（Hexo / Gatsby）：**

| 工具 | 21 页构建耗时 | 说明 |
|---|---|---|
| **Hugo** | **0.13 秒** | Go 编写 |
| Hexo | 2–5 秒 | Node.js，需启动解释器 |
| Gatsby | 30 秒+ | React SSR，首次更慢 |

文章越多差距越大。100 篇文章时，Hugo 仍能在 1 秒内完成，Node.js 系可能需要几十秒。

## 四、CPU 占用：空闲时 0%

```bash
$ docker stats --no-stream
NAME          CPU %    ...
blog-nginx    0.00%    ...
```

**没有访问时，CPU 占用是 0。** Nginx 在 `epoll` 上阻塞等待连接，不消耗 CPU。

只有在处理请求时才会用到 CPU。前面测过，2 核机器能跑 3 万 QPS（bridge 模式）。

## 五、这些数字意味着什么

### 1 核 512M 的机器够用吗？

**够。** 静态站的资源需求极低：

- 内存：10 MB（Nginx）+ 系统开销约 200 MB = **210 MB**
- 磁盘：**50 MB** 左右
- CPU：空闲 0%，峰值时才用

**1 核 512M 完全能跑，甚至还有余量。**

真正需要更多资源的是**构建**环节（68 MB 峰值内存），但构建是一次性的，而且可以在本地做完再上传。

### 什么时候需要更大的配置

| 场景 | 建议配置 | 原因 |
|---|---|---|
| 纯静态博客（本文场景） | 1 核 512M | 资源占用极低 |
| 静态站 + 评论系统（Waline） | 1 核 1G | 评论服务需 ~300 MB |
| 静态站 + 全文搜索服务 | 1 核 1G | 搜索索引需常驻内存 |
| 加数据库 | 2 核 2G 起 | 数据库吃内存 |
| 需要在服务器上构建 | 2 核 1G | 构建峰值 68 MB，1 核也够但慢些 |

## 六、真正的瓶颈不是这些

虽然 CPU、内存、磁盘都绰绰有余，但**实际体验的瓶颈在别处**：

### 1. 带宽

这台机器的公网带宽有限。10.24 MB 的内存占用没有意义，**能发出去多少数据才决定用户体验**。

一个 8 KB 的 HTML，1 Mbps 带宽每秒只能让 15 个用户同时加载。这才是限制。

### 2. 网络延迟

香港节点到国内用户，RTT 通常在 30–80 ms。开 HTTPS 还要加握手时间。

**这部分可以用 CDN 优化，跟服务器配置无关。**

### 3. 首次加载的静态资源

如果用了字体、图标库、CDN 上的第三方 JS，这些加载时间往往比 HTML 本身长得多。

**这才是优化重点，不是升级服务器。**

## 七、一个反直觉的结论

测完这些数据，我最大的感受是：

> **给静态博客升级服务器配置，几乎是纯粹的浪费。**

3 万 QPS 意味着什么？日均 100 万 PV 的站点，峰值也就几百 QPS。**这台 2 核机器能扛住比「日均百万 PV」高两个数量级的压力。**

真正的优化顺序应该是：

1. **加 CDN**（收益最大，成本最低）
2. **优化图片/资源体积**（直接影响首屏）
3. **减少第三方依赖**（少加载一个外部 JS 就快一截）
4. **……**
5. **最后才考虑升服务器配置**

## 小结

| 问题 | 答案 |
|---|---|
| 静态站吃多少内存？ | **10 MB**（Nginx 常驻） |
| 构建需要多少？ | 峰值 **68 MB**，耗时 **0.13 秒** |
| 1 核 512M 够吗？ | **够，而且有余量** |
| 需要升配置吗？ | **基本不需要，优化带宽和 CDN 更有用** |

静态站的最大价值不是「快」，而是**「便宜到可以忽略成本」**。一台最低配的云服务器，就能承载一个日访问量很大的个人站点。
