## 事情的开始

给博客加了个留言板功能。部署完，我本地测试：

- 页面能打开 ✅
- 组件正常渲染 ✅
- 提交评论成功 ✅
- 数据库有记录 ✅

然后用户反馈：**「提交后没反应。」**

我第一反应是：**「不可能，我这边好好的。」**

这句话，就是后面几小时折腾的开端。

## 第一次误判：怀疑限流

我想到之前设了个频率限制：

```yaml
IPQPS: "60"    # 同一个 IP 60 秒内只能发一条
```

用户可能是连发了两次被拦了？

查服务端日志，确实看到了：

```json
{"errno":1000,"errmsg":"Comment too fast!"}
```

**看起来找到了原因。** 改成 10 秒，通知用户重试。

**结果：还是不行。**

### 这次错在哪

我看到 `Comment too fast!` 就认定是根因，但没确认：

- 这个错误是用户触发的那次请求吗？
- 用户看到的报错是这个吗？
- 如果是这个错误，前端应该显示提示，为什么用户说「没反应」？

**我把「一个可能的原因」当成了「确定的原因」。**

## 第二次误判：怀疑 CDN 不稳定

用户反馈是「没反应」，我开始怀疑前端 JS 没加载。

页面依赖：

```javascript
import { init } from 'https://unpkg.com/@waline/client@v3/dist/waline.js';
```

`unpkg.com` 在国内时好时坏。测了一下，**282 KB 的文件，首次加载 2 秒**。

判断：**这个 CDN 慢，导致组件没初始化。**

于是把 JS/CSS 全部下载到自己的服务器：

```bash
mkdir -p site/static/vendor/waline
curl -o site/static/vendor/waline/waline.js https://unpkg.com/@waline/client@v3/dist/waline.js
```

页面改成：

```javascript
import { init } from '/vendor/waline/waline.js';
```

**结果：用户还是说不行。**

### 这次错在哪

方案本身是对的（本地化 CDN 是好实践），**但我又是在猜**。

我没有证据证明「CDN 是这次问题的原因」。我只是觉得「CDN 可能不稳」，就动手改了。

改完之后没有验证「用户现在能拿到了吗」，就直接等反馈。

## 第三次误判：以为改好了

本地化之后我有充分理由相信修好了：

- 资源本地化 ✅
- 服务端测试通过 ✅
- 浏览器端到端测试通过 ✅
- 提交成功、数据入库 ✅

我甚至截图了，看起来完全正常。

**结果：用户说「还是不行」。**

这次我开始怀疑**用户的环境**——是不是他浏览器缓存了旧版本？

于是加了禁止缓存：

```nginx
location = /message-board/ {
    add_header Cache-Control "no-store, no-cache, must-revalidate, max-age=0";
    add_header Pragma "no-cache";
}
```

**结果：仍然不行。**

### 这次错在哪

我在**猜用户的环境**，而且猜错了方向。

直到用户说了一句话，我才意识到问题的严重性：

> **「尝试了别的浏览器也不行，显示 Failed to fetch」**

**「别的浏览器也不行」**——这排除了「单个浏览器缓存」的假设。

**「Failed to fetch」**——这是个具体的错误信息，不是「卡住」。

我一直在处理「没反应」，但用户实际遇到的是「报错」。**我们讨论的都不是同一件事。**

## 转折点：去看服务器到底记录了什么

前面几轮，我都在**测自己的环境**。这次我改了一个动作：

**去查用户的 IP 在服务器上留下了什么请求记录。**

```bash
grep "117.80.192.151" data/nginx-logs/access.log | tail -20
```

看到了：

```
"GET /message-board/" 200 3631
"GET /message-board/" 200 3631
"GET /message-board/" 200 3631
```

**3631 字节。**

而服务器上的文件是：

```bash
$ stat -c%s site/public/message-board/index.html
9183
```

**9183 字节。**

**用户收到的不是我部署的那个页面。**

而且——**日志里没有任何 `/comment/api/` 请求**。说明用户那份页面（3631 字节）里的 JS 根本没发起 API 请求。

这才是真相：**用户拿到的是一份旧页面，那份旧页面根本不能提交评论。**

## 回头检查：为什么会变成 3631 字节

顺着这个线索查，发现了真正的原因：

那篇文章的 front matter 写的是：

```yaml
date: 2026-11-19T18:00:00+08:00
```

**而当时是 11-18 17:50。**

Hugo 不构建未来日期的页面。所以从那一刻起，`/message-board/` 就变成了 404。

用户看到的「3631 字节」，是他浏览器缓存的**更早版本**——那个版本是在我改配置之前的，功能是坏的。

**一个小小的日期错误，导致了整个功能不可用，而我花了很久才找到。**

## 六步排查法

这次经历让我总结出一个流程：

### 第 1 步：先拿「用户实际收到的内容」

**不要先测**，先看证据。

```bash
# 找到用户的 IP
grep "用户IP" access.log | tail -20

# 看他请求了什么，返回了什么状态和大小
```

这一步能立刻区分几种完全不同的情况：

| 日志显示 | 说明 |
|---|---|
| 有请求，200，大小正常 | 服务端没问题，问题在前端 |
| 有请求，200，**大小不对** | 内容有问题（缓存/构建/替换） |
| 有请求，404/500 | 服务端确实有问题 |
| **没有请求** | 请求根本没发出去 |

**这次就是「大小不对」——但我前几轮都没查过。**

### 第 2 步：对比「我测到的」和「用户看到的」

```bash
# 我这边的结果
curl -sI http://myserver/path | grep -i "content-length"
# Content-Length: 9183

# 用户日志里的
# 200 3631
```

**不一致 = 中间有东西改写了内容。**

可能是：CDN、缓存代理、浏览器缓存、网络运营商劫持。

### 第 3 步：验证不是「我的测量工具骗了我」

我之前一直用 headless 浏览器测，但**它访问不了海外 IP**（返回 `ERR_BLOCKED_BY_CLIENT`）。

于是我改用「下载 HTML → 本地渲染」的方式测试。

**这个方式验证的是「代码逻辑对不对」，但没有验证「用户能不能拿到这份代码」。**

**测试工具的局限，就是你的盲区。**

### 第 4 步：最小化验证

与其改一堆东西，不如用一个最直接的方法排除变量：

```
http://47.238.215.116/message-board/?t=123456
```

**加个随机参数**，任何缓存层都会认为是新地址，强制回源。

如果这样能正常，就证明是缓存问题。

### 第 5 步：改一处，验一处

这次我犯的错是**一次改好几个地方**：

- 换 CDN
- 加禁止缓存
- 改限流

结果改完还是不行，**不知道是哪个没生效，还是都没生效**。

**正确做法**：一次只改一个变量，改完立刻验证用户端看到的变化。

### 第 6 步：承认「我的测试通过」不等于「用户能用」

这是最难接受的。

我的所有测试都显示「功能正常」。但**测试环境和用户环境不是一回事**：

| 我的环境 | 用户环境 |
|---|---|
| 本地下载 HTML 后渲染 | 浏览器直接访问 |
| 无缓存干扰 | 可能有缓存/代理 |
| 我的网络路径 | 用户的网络路径 |
| 我改完立刻测 | 用户可能拿到旧缓存 |

## 如果重来一次，我会这样做

### 第一次收到「没反应」时

```bash
# 1. 立刻查用户 IP 的请求日志
grep "用户IP" access.log | tail -20

# 2. 看有没有请求、状态码、大小
# 3. 对比我这边 curl 的结果
curl -sI http://server/path | grep -i content-length
```

**三分钟内就能定位方向。**

### 而不是

- ❌ 先猜是限流 → 改限流 → 等反馈
- ❌ 再猜是 CDN → 换 CDN → 等反馈
- ❌ 再猜是缓存 → 加缓存头 → 等反馈

**每一轮都花时间是「猜 + 改 + 等」的循环，而不是「查证据」。**

## 一个更深的教训

这次最本质的问题是：**我把「用户描述的现象」和「我以为的现象」混为一谈了。**

用户说「没反应」，我理解成「点了按钮卡住」。
实际是「页面本身是坏的，根本没有按钮可用」。

**「没反应」这三个字，可能对应完全不同的十种情况。**

所以第一步永远是：**让用户提供具体信息。**

| 模糊描述 | 需要追问的 |
|---|---|
| 「没反应」 | 有报错吗？报什么字？页面长什么样？ |
| 「打不开」 | 白屏还是报错？什么错误？ |
| 「很慢」 | 大概几秒？一直慢还是偶尔？ |
| 「不行」 | 具体哪里不行？点哪里？ |

**好的提问能省掉几小时。**

## 小结

| 阶段 | 错误做法 | 正确做法 |
|---|---|---|
| 收到反馈 | 先猜原因 | 先查证据 |
| 排查方向 | 测自己的环境 | 查用户的请求日志 |
| 验证方式 | 只测代码逻辑 | 也测用户能否拿到 |
| 修改节奏 | 一次改多处 | 一次改一处 |
| 沟通 | 接受模糊描述 | 追问具体细节 |

**一句话：先看证据，再动手。**

别让「我这边是好的」成为你排查的起点——那是终点才该有的结论。
